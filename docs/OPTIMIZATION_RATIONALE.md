# 项目优化说明与决策逻辑

## 1. 优化目标

原项目已经能抓取弹幕、统计高频词、下载视频和导出 Excel，但更接近一组能够运行的脚本。项目还需要回答三个问题：

1. 用户能否快速理解并完成核心任务。
2. 代码在异常输入、网络波动和并发请求下是否可靠。
3. 其他开发者能否测试、部署并继续维护它。

因此这次优化不以增加零散功能为目标，而是把项目整理成一套完整产品：以弹幕洞察为核心，以任务系统承载耗时操作，以测试、容器和 CI 证明工程质量。

## 2. 核心定位调整

### 原有问题

- 首页来自通用 landing page 模板，项目能力藏在多个展示区块中。
- 高频词、峰值、导出分别请求并重复抓取同一个视频。
- 视频下载与弹幕分析处于同等位置，核心价值不够明确。

### 修改方案

- 首屏改成可直接操作的分析工作台。
- 一次分析同时生成视频信息、高频词、时间轴、多个峰值与聚合指标。
- 下载保留为分析结果后的辅助动作，主流程聚焦数据洞察。
- 增加历史记录，分析结果能够再次查看，不再是一次性响应。

### 为什么这样改

作品的第一屏应该展示真实业务流程，而不是介绍功能。统一分析流程既减少外部请求，也让后端能够保存完整结果，前端则能围绕一个明确的数据对象组织状态。

## 3. 后端分层

### 原有问题

`views.py` 同时包含 HTTP 参数处理、页面抓取、XML 解析、分词、Excel、下载和 Pygame。任何一处修改都可能影响其他功能，也很难在不访问网络的情况下测试。

### 修改方案

| 模块 | 职责 |
| --- | --- |
| `views.py` | HTTP 输入输出和状态码 |
| `services/validation.py` | URL 与数值参数校验 |
| `services/bilibili.py` | 页面、初始化数据与弹幕获取 |
| `services/analysis.py` | 分词、时间轴和峰值算法 |
| `services/export.py` | Excel 生成 |
| `services/download.py` | yt-dlp 下载与体积限制 |
| `tasks.py` | 长任务生命周期和持久化 |
| `task_queue.py` | 线程池与 Celery 适配 |

### 为什么这样改

为了隔离变化：

- Bilibili 页面变化时，只修改客户端和解析测试。
- 算法变化时，不影响 HTTP 接口。
- 从本地线程迁移到 Celery 时，不改业务任务。
- 单元测试可以直接传入固定数据，不依赖外部网络。

## 4. API 与任务模型

### 原有问题

旧接口在一次 HTTP 请求中完成网络抓取和计算。网络慢时请求会长时间挂起，浏览器无法知道进度，Web 进程也会被占用。

### 修改方案

- 写接口统一放在 `/api/v1/`。
- 创建分析或下载时返回 HTTP 202 和任务 UUID。
- 前端轮询任务状态，显示 `pending`、`running`、`success`、`failed` 与进度。
- 开发环境用有界线程池，生产环境通过 Celery + Redis 执行。
- 使用 `Video`、`AnalysisTask`、`DanmakuSummary` 和 `ExportRecord` 保存业务状态。

### 为什么采用双模式

本地体验不应强制安装 Redis，因此默认线程池只需要 Python 和 Node.js。生产环境需要跨进程队列、失败隔离和可扩展 Worker，因此 Docker 使用 Celery。两种模式共享同一个 `execute_task`，避免出现两套业务实现。

线程池适合单机演示，不具备跨进程持久队列能力。Celery 才是部署场景的推荐模式，这一取舍已通过环境变量显式表达。

## 5. 外部请求安全

### 原有问题

后端直接请求用户传入的 URL，会产生服务端请求伪造风险。关闭 CSRF 的写接口也可能被第三方页面利用。

### 修改方案

- 只允许 `bilibili.com`、`www.bilibili.com`、`m.bilibili.com` 与 `b23.tv`。
- 拒绝相似域名、账号信息、自定义端口和非 HTTP(S) 协议。
- 关闭自动重定向，每次跳转都重新校验目标，最多四次。
- 恢复 Django CSRF 中间件，前端显式初始化并发送 CSRF Token。
- CORS 使用来源白名单并允许凭据。
- 对分析、导出和下载设置单 IP 限流。
- 限制请求体和下载文件体积。
- Cookie 文件、密钥、数据库和生成文件不进入 Git。

### 为什么不能只检查 URL 是否包含 “bilibili”

`bilibili.com.attacker.example` 同样包含该字符串，但实际主机属于攻击者。只有解析 URL 后比较标准化 hostname，并逐次检查重定向，才能把外部请求限定到预期域名。

## 6. 抓取可靠性

### 修改方案

- Requests Session 复用连接。
- 对 429、500、502、503、504 实施有限次数指数退避重试。
- 页面请求使用连接与读取超时。
- 优先解析 `window.__INITIAL_STATE__` 中的结构化 JSON，CID 保留正则兜底。
- 抓取结果按标准化 URL 缓存，默认十分钟。
- 统一把内部异常转换为用户可理解的信息，日志保留任务 ID。

### 为什么这样改

外部页面抓取不可避免地受网络和页面结构影响。重试解决短暂故障，超时避免无限等待，缓存减少重复流量，结构化解析则比针对整段 HTML 的多个正则更稳定。

## 7. 分析算法

### 高频词

提取中文文本后使用 jieba 分词，过滤单字和常见口语停用词。Top N 由用户配置，默认 20，图表显示前 10 个以保持可读性。

### 时间轴

按固定秒数聚合弹幕，并补齐没有弹幕的时间桶。补零非常重要，否则折线图会把两个相隔较远的时间点错误地连接成连续密度。

### 精彩片段

旧算法先把时间戳四舍五入到整秒，再统计三秒窗口，会损失亚秒信息。新算法：

1. 对原始浮点时间戳排序。
2. 使用左右指针维护精确滑动窗口。
3. 按弹幕数排序候选窗口。
4. 选择多个互不重叠的片段。

排序复杂度为 `O(n log n)`，滑动扫描为 `O(n)`。结果既保留精度，也避免向用户推荐高度重叠的同一段内容。

## 8. 前端技术与交互

### 修改方案

- 从 Create React App 迁移到 React 19 + Vite 6。
- 移除 jQuery、Bootstrap、Font Awesome、ReactPlayer 和模板组件。
- 使用 ECharts 展示关键词和完整密度时间轴。
- 分析结果出现时再按需加载图表模块，降低首屏脚本体积。
- 使用 Lucide 统一操作图标。
- 增加加载进度、失败状态、空状态、历史记录和移动端布局。
- 使用真实封面、标题、UP 主与 BV 号建立结果上下文。

### 版本选择逻辑

[React 官方已停止维护 Create React App](https://react.dev/blog/2025/02/14/sunsetting-create-react-app)，并推荐使用构建工具或框架启动新项目；[React 版本页](https://react.dev/versions)将 19.2 列为当前文档版本，因此迁移到 React 19。

[Vite 当前文档](https://vite.dev/guide/)中的最新主版本要求 Node.js 20.19+，而项目目标机器当前是 Node.js 20.17。为了保证现有机器可直接运行，本次使用仍支持该环境的 Vite 6，而不是为了追新强制升级运行时。

[Django 5.2 发布说明](https://docs.djangoproject.com/en/5.2/releases/)显示 5.2 系列仍持续获得修复，因此后端由 5.1 升级到 5.2 的维护版本。

### 为什么移除旧依赖

旧页面同时加载 React、jQuery 和 Bootstrap，存在重复能力、全局样式干扰和更大的依赖面。当前页面只保留实际使用的库，组件状态由 React 管理，布局由项目自己的 CSS 控制，维护边界更清楚。

## 9. 数据导出

旧 Excel 只有单行视频信息，并且每次导出重新访问页面。新导出直接读取已保存的分析结果，包含：

- 视频概览
- 高频关键词
- 弹幕时间轴
- 精彩片段

这既避免重复抓取，也使导出内容与页面看到的结果完全一致。工作表包含表头样式、冻结行、筛选器和自动列宽，方便面试时展示实际交付质量。

## 10. 测试策略

测试重点不是追求行数，而是覆盖最容易导致线上问题的行为：

- 允许和拒绝的 URL 边界
- 相似域名、账号信息与自定义端口
- Bilibili 初始化 JSON、CID 和弹幕 XML 解析
- 亚秒级精确滑动窗口
- 非重叠精彩片段和空时间桶
- CSRF、限流、参数错误与任务创建
- 历史记录、详情和 Excel 导出

测试使用固定 HTML/XML 样本，不访问真实 Bilibili，因此结果稳定、运行快速，也不会给外部站点带来测试流量。

## 11. 部署与持续集成

### Docker Compose

容器环境包含：

- Nginx 托管前端并代理 API、静态文件和下载文件
- Gunicorn 运行 Django
- Celery Worker 执行耗时任务
- Redis 提供队列和缓存
- PostgreSQL 提供多进程场景下更可靠的数据存储

本地仍使用 SQLite，降低首次运行门槛。容器改用 PostgreSQL，是因为 Django Web 进程与 Celery Worker 会并发访问数据库，SQLite 不适合作为该部署模式的长期选择。

### GitHub Actions

每次推送和 Pull Request 自动执行：

- Python 依赖安装
- Ruff 静态检查
- Django system check
- 后端测试
- 前端依赖锁定安装与生产构建

CI 的价值是把“在我的电脑上可以运行”变成仓库可重复验证的事实。

直接依赖使用精确版本保证构建可复现，Dependabot 每周检查 Python、npm 与 GitHub Actions 更新，并通过 Pull Request 接受测试后再升级。

## 12. 日志与可观察性

后端日志使用 JSON 格式，任务成功或失败都会记录任务 ID，便于在容器日志平台中检索。健康检查接口供 Docker 和部署平台判断服务状态。

当前没有引入大型监控平台，避免给作品项目增加维护成本。后续真正上线时可继续接入 Sentry、OpenTelemetry 和队列监控。

## 13. 表达建议

可以按下面的因果链讲解，而不是只罗列技术名词：

1. 发现同步抓取会阻塞 HTTP 请求，所以引入持久任务状态，并提供本地线程和生产 Celery 两种执行器。
2. 发现用户 URL 会被服务器访问，所以做了精确域名白名单和逐跳重定向校验。
3. 发现旧峰值算法会四舍五入时间，所以改为双指针滑动窗口并用测试锁定亚秒行为。
4. 发现多个接口重复抓取，所以一次生成完整摘要并持久化，历史与导出都复用结果。
5. 发现项目只能在原电脑运行，所以补齐锁文件、环境模板、Docker Compose 和 CI。

这些内容分别体现需求分析、安全意识、算法能力、架构设计和工程交付，比单纯展示框架名称更有说服力。

## 14. 有意保留的边界

- 不绕过登录、付费或地区访问限制。
- 不提供批量抓取与批量下载入口。
- 不在仓库中提供真实 Cookie。
- 不承诺 Bilibili 私有页面结构永久稳定。
- 本地线程模式适合演示，不代替生产队列。

明确边界能避免为了功能数量牺牲合规性和可维护性。

## 15. 后续可继续演进

按收益优先级排序：

1. 增加情感倾向、关键词共现与分段主题变化。
2. 接入 Sentry 和 OpenTelemetry，统计任务耗时与失败类型。
3. 增加用户账户和私有分析历史。
4. 为解析器建立更多页面类型样本，包括多 P 视频。
5. 使用 Server-Sent Events 替代固定间隔轮询。
6. 增加端到端浏览器测试与公开演示环境。

这些内容没有在本次一次性加入，是为了控制范围，优先把核心分析流程做到可用、可测、可部署。
